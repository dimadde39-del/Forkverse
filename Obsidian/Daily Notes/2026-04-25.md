## MonteRun income delay validation

Validated the income delay task as the fourth/final ParanoidValidator pass.

Scope audited:
- `engine/monte_carlo.py`
- `api/parse.py`
- `components/SimulatorClient.tsx`
- `components/WhatIfControls.tsx`

Canonical constraints applied:
- MonteRun remains a deterministic survival engine, not an AI probability engine.
- LLM parsing can extract `income_delay_months`, but the NumPy core owns all math.
- `income_delay_months` defaults to `0`.
- Delays greater than the horizon must not crash.
- Delay handling must stay vectorized, not loop over simulations.

Audit findings:
- `MonteRunParams` now carries `income_delay_months: int = 0`.
- `simulate(...)` accepts `income_delay_months` without capping it to `months`, so values such as `240` are valid input even for a 6 or 24 month horizon.
- `_simulate_capital_paths(...)` applies the delay with vectorized NumPy slicing:
  - `delay = min(income_delay_months, income_noise.shape[1])`
  - `realized_income[:, :delay] = 0.0`
- This clamps to the matrix width, so `income_delay_months > horizon` zeros all simulated income columns and never indexes past the array.
- There is no loop over simulation paths for the delay behavior.
- Parser prompt includes the required instruction: "Extract how many months the user will wait before getting their first income. Default is 0."
- Parser prompt also includes the guard added during validation: "Do not ask clarification only because income_delay_months is absent; use 0."
- Parser normalization defaults missing delay to `0`, preserves explicit integer delay, and forwards it into `MonteRunParams` and legacy `simulate(...)`.
- What-If UI clamps delay controls to `0..12` with step `1` and the label `Задержка дохода (мес) / Income Delay (months)`.
- Existing debounced recalculation path is preserved through `useDebouncedSimulation`.
